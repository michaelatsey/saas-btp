### ADRs (all accepted)
- ADR-PROD-001 — market entry through Safety, not Quality. Rationale grounded in the
  2026 Ivorian market: mandatory site insurance bill, SPS coordination + penal
  liability (law 2024-239), ~75% fatal accidents from falls/crushing/electrocution,
  QHSE tooling already framed around constats/incident reports/action plans.
- ADR-ARCH-002 — CorrectiveActions as a separate bounded context. Reacts to Safety
  and Quality via integration events (MicroKit.Messaging); no compile-time coupling;
  the differentiator (corrective-action lifecycle) modelled once.
- ADR-ARCH-003 — Increment 1 field client = offline PWA (Next.js + PowerSync Web),
  single codebase for field + dashboard. Native Expo deferred to Phase 2. ACCEPTED
  but GATED by a technical spike (PowerSync-web offline + camera on a real target
  Android) before the full build; if the spike fails, escalate to Expo.

### Conventions
- Naming standard (conventions/naming.md): per-layer — C# PascalCase, JSON/API
  camelCase (contract boundary), TS camelCase (generated), Postgres snake_case, enum
  values camelCase tokens, UI labels localized (French first). Named once in C#,
  layers translate automatically.
- Language: all repo files and sessions in English. Our working exchanges in French
  with English technical terms. UI labels localized (French first).
- Steering vs specs separation: scope-phase-1.md is steering (strategy/increments/
  metrics/risks/validation); detailed fields/rules live in specifications/.

### Product specifics confirmed
- severity field kept on constat (drives dashboard + escalation).
- Constat invariants validated (accident requires corrective action before resolved;
  critical severity requires a photo; resolved only when all actions closed; one site
  per constat; soft delete only).
