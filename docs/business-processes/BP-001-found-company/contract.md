# BP-001 — Contract

What founding a company introduces in software, and what guarantees each invariant and scenario
of `process.md` and `acceptance.md` in production. Rules are referenced by identifier, never
restated. ADR-ARCH-032 applies except its §2 call path and its §4 creation order, which
ADR-ARCH-033 replaces.

## 1. Owner and boundary

- Every element of this process belongs to the Access module and its `access` schema
  (ADR-ARCH-031 §1). The person is known only through the identity provider's user identifier
  and their profile (ADR-ARCH-031 §2).
- TSK-2 is one unit of work of Access, in one explicit transaction whose first statement sets the
  subject (ADR-ARCH-033 §4). No other module takes part.
- "Company founded" publishes no integration event: no consumer needs one, and an outbox comes
  with the first consumer (ADR-ARCH-032 §1).

## 2. Interface

Three operations under `/api/v1` (ADR-ARCH-018), each requiring an authenticated caller. They
appear in the committed `apps/api/openapi/v1.json`.

### Found a company — `POST /api/v1/organizations`

Body: `organizationId` (the reference, a UUIDv7 generated by the client before the first
submission, `naming.md` "Aggregate identifiers"), `organizationName`, `workspaceName`. The body
names no founder (BP001-R2). Every other identifier, and every timestamp, is set by the API
before the write, from an injected clock; the database generates none.

| Status | When | Body |
|---|---|---|
| 201 | The organization is founded by this request | The organization: `id`, `name`, `status`; `Location` names it |
| 200 | `organizationId` identifies an organization whose current owner is the caller | The same representation of that organization; the payload is not compared |
| 409 | `organizationId` identifies any other organization, including one the caller belongs to without owning it | A problem stating only that the reference is in use |
| 422 | A name is missing (empty or only spaces), or `organizationId` is not a UUIDv7 | A validation problem whose `errors` names the field: `organizationName`, `workspaceName` or `organizationId` |
| 400 | The body cannot be read or bound | A problem, no detail |
| 401 | No caller, or a token the API rejects | No body |
| 403 | The caller does not meet the identity level of BP001-D1 | A problem stating that the contact must be confirmed |

Checks run in this order: authentication (401), the body (400, 422), the identity level (403),
then the unit of work (201, 200, 409). 403 is used for this one reason; a row hidden by the
policies is never answered 403 (ADR-ARCH-032 §5). Every refusal is a problem details response
(RFC 9457).

### List the workspaces I can enter — `GET /api/v1/workspaces`

The workspaces where the caller holds a current access: `id`, `name`, `organizationId`. No filter,
no pagination.

### Read an organization — `GET /api/v1/organizations/{id}`

200 with `id`, `name`, `status` when the policies let the caller see it; 404 otherwise, whether or
not it exists (ADR-ARCH-032 §5). No operation exposes an organization's owner or members.

## 3. Replay and claim

The reference is the idempotency key (`naming.md` "Aggregate identifiers", BP001-R3):

- A founding whose reference is already used fails on the primary key of `access.organizations`,
  which unique checks enforce outside row level security. The unit of work rolls back.
- The API then reads, in a new transaction under the same subject, whether the caller is the
  **current owner** of that organization. If so, it answers 200 with it; otherwise 409.
- The test reads ownership, not visibility: a process that lets members see their organization
  (BP-004) must not turn a member's submission into a replay (BP001-AC-21).
- Every refusal is logged internally with its class (ADR-ARCH-032 §5).

## 4. Failure, retry and concurrency

- **Failure.** The founding commits whole or not at all, profile included (TSK-2); the API never
  writes to the identity provider. The client resubmits the same request (§6).
- **Same request twice, or at once.** The second submission waits on the primary key until the
  first commits, fails, and answers 200 through §3.
- **Profile.** Two first foundings of the same person at the same moment conflict on the profile's
  unique key; the losing unit of work is retried once, from the start, in a new transaction.
- **Identity level.** Checked on every submission, so a level lost while a request waited refuses
  it (BP001-AC-10).

## 5. Security guarantees

- The subject, its transaction scope and its trust boundary: ADR-ARCH-032 §3, ADR-ARCH-033 §4.
- Insert order, insert and select policies, the paired workspace visibility and
  `access.may_act_in`: ADR-ARCH-033 §5. Exactly one current owner: ADR-ARCH-033 §6.
- BP-001 creates no `UPDATE` or `DELETE` policy on any Access table: under forced row level
  security (ADR-ARCH-027, ADR-ARCH-028) no founded record can be changed or removed through the
  API until a process adds one.
- In this process, an organization is visible to its current owner only.
- Rules the policies do not hold, enforced by the domain and proven by its tests (ADR-ARCH-032 §4):
  the founder's access covers the first workspace only (BP001-R4); ownership and membership grant
  no access (INV-ACCESS-05).
- Refusals reveal nothing beyond "in use" or "not found" (ADR-ARCH-032 §5, INV-ACCESS-09).

## 6. The client's founding-request store

What TSK-1, BP001-R6 and BP001-D2 require of the client, without naming a technology:

- A request is keyed by its reference, assigned when the description starts, and kept until it is
  answered 201 or 200, or abandoned; it survives closing the application and the loss of the
  connection.
- It belongs to the identity provider's user who described it. It is shown and submitted only
  while that user is signed in.
- After its first submission its names cannot change, except after a 422.
- 403, 401 and failures keep it unchanged and resubmit the same request once possible; 409 gives
  it a new reference and keeps its names.
- The first workspace name is offered as the company name.

**Not covered by the pilot #138**, which delivers the backend: BP001-AC-02, 07 (the description
kept), 12, 16, 18, 22, and the device part of BP001-AC-10. BP001-R6 is therefore not verified
until the client is built.

## 7. Guarantors

Tests carry the identifier at the start of their name, with `-` written `_`
(`BP001_AC_13_…`, `INV_ACCESS_06_…`). Test projects follow ADR-ARCH-034 §6; "Integration" is
`SaasBtp.Access.Adapters.IntegrationTests`, run as `saasbtp_api` on a database migrated by the
runner.

## 8. Obligations carried from July (#162)

| Obligation | Status |
|---|---|
| Identifiers and timestamps exist before the write | Met: the reference from the client, every other identifier and timestamp from the API (§2). |
| One indivisible step | Met: one unit of work (§1, §4). |
| The founder from the signed-in context | Met: BP001-AC-06. |
| Three separate relations | Met: INV-ACCESS-05. |
| One current membership, access and owner | Met: INV-ACCESS-02, 06, 07. |
| Access revocable, history kept | Met: INV-ACCESS-07; ending an access is BP-005's. |
| An explicit policy per role | Superseded by ADR-ARCH-027, ADR-ARCH-028 and `sql.md` RLS. |
| "May act in this workspace" expressed once and proven equivalent wherever evaluated | Superseded in part: the API never evaluates it (ADR-ARCH-032 §5), and the database expresses it once, `access.may_act_in` (ADR-ARCH-032 §2, ADR-ARCH-033 §1). Synchronization's agreement is tested when it is built (ADR-ARCH-032, Consequences). What remains is met by `INV_ACCESS_07_WorkspaceListMatchesMayActIn`: on the same data, `GET /api/v1/workspaces` returns exactly the workspaces for which `access.may_act_in` is true. Equality with workspace visibility is not required (ADR-ARCH-033 §5). |
| Workspace access can source synchronization | Met in form: the access carries profile, workspace and organization, indexed on the three (ADR-ARCH-033, Consequences); proven with synchronization. |

## 9. Open points

Cited, not decided here:

- Token validation in the API and the reading of the "confirmed contact" level: the identity ADR
  of BP-002. BP001-AC-09 to 11 depend on it.
- Audit columns of the Access tables: #184.
- MicroKit.Result and MicroKit.Persistence declared sound before implementation (ADR-ARCH-035 §2).
- Abuse protection, including any rate limit: open question of `process.md`; no `429` is part of
  this contract.
