# BP-001 — Contract

What founding a company introduces in software, and what guarantees each invariant and scenario
of `process.md` and `acceptance.md` in production. Rules are referenced by identifier, never
restated. ADR-ARCH-032 applies except its §2 call path and its §4 creation order, which
ADR-ARCH-033 replaces; those two parts are history.

## 1. Owner and boundary

- Every server element of this process belongs to the Access module and its `access` schema
  (ADR-ARCH-031 §1). The person is known only through the identity provider's user identifier
  and their profile (ADR-ARCH-031 §2).
- The founding-request store (§6) belongs to the client application.
- TSK-2 is one unit of work of Access (ADR-ARCH-033 §4). No other module takes part.
- "Company founded" publishes no integration event: no consumer needs one (ADR-ARCH-032 §1).

## 2. Interface

Three operations under `/api/v1` (ADR-ARCH-018), each requiring an authenticated caller. They
appear in the committed `apps/api/openapi/v1.json`. Organization `status` is sent as `declared`
or `verified` (`naming.md`, Enum value style).

### Found a company — `POST /api/v1/organizations`

Body: `organizationId` (the reference, a UUIDv7 generated by the client before the first
submission, `naming.md` "Aggregate identifiers"), `organizationName`, `workspaceName`. The body
names no founder (BP001-R2), and properties the operation does not define are ignored. Every
other identifier, and `created_at` (`sql.md` Audit / lifecycle), is set by the API before the
write, from an injected clock; the database generates none.

| Status | When | Body |
|---|---|---|
| 201 | The organization is founded by this request | The organization: `id`, `name`, `status`; `Location` names it |
| 200 | `organizationId` identifies an organization whose current owner is the caller (§3) | The same representation of that organization; the payload is not compared |
| 409 | `organizationId` identifies any other organization, including one the caller belongs to without owning it | Only that the reference is in use |
| 422 | A name is missing (empty or only spaces) or longer than 200 characters, or `organizationId` is a UUID that is not version 7 | The field at fault: `organizationName`, `workspaceName` or `organizationId` |
| 400 | The body cannot be read or bound, `organizationId` not being a UUID included | No detail |
| 401 | No caller, or a token the API rejects | No detail |
| 403 | The caller does not meet the identity level of BP001-D1 | Only that the contact must be confirmed |
| 500 | Any other failure, the profile retry of §4 exhausted included | No detail, never naming a constraint or a row (ADR-ARCH-032 §5) |

Checks run in this order: authentication (401), the body (400, 422), the identity level (403),
then the unit of work (201, 200, 409). 403 is used for this one reason; a row hidden by the
policies is never answered 403 (ADR-ARCH-032 §5).

### List the workspaces I can enter — `GET /api/v1/workspaces`

The workspaces for which `access.may_act_in` is true for the caller: `id`, `name`,
`organizationId`. No filter, no pagination. It is the read that lets a client show where the
caller may act; it decides no access to data, which stays the policies' (ADR-ARCH-032 §5).

### Read an organization — `GET /api/v1/organizations/{id}`

200 with `id`, `name`, `status` when the policies let the caller see it; 404 otherwise, whether or
not it exists (ADR-ARCH-032 §5). No operation exposes an organization's owner or members.

## 3. Replay and claim

The reference is the idempotency key (`naming.md` "Aggregate identifiers", BP001-R3):

- A founding whose reference is already used fails on the primary key of `access.organizations`
  (ADR-ARCH-032, Context). The unit of work rolls back.
- The API then reads, in a new transaction under the same subject, whether the caller is the
  organization's **current owner**: the profile of the ownership that
  `access.organizations.current_ownership_id` references (ADR-ARCH-033 §6). If so, it answers
  200 with the organization; otherwise 409. An ownership row naming the caller that the
  organization does not reference, a former one or an orphan, makes the caller no owner.
- The test reads current ownership, not visibility: a process that lets members see their
  organization (BP-004) must not turn a member's submission into a replay.

## 4. Failure, retry and concurrency

- **Failure.** The founding commits whole or not at all, profile included (TSK-2); the API never
  writes to the identity provider.
- **Same request twice, or at once.** The second submission waits on the profile's unique key or
  the organization's primary key until the first commits, then answers 200 through §3, after the
  profile retry if needed.
- **Profile.** Two first foundings of the same person at the same moment conflict on the profile's
  unique key; the losing unit of work is retried once, from the start, in a new transaction.
- **Identity level.** Checked on every submission, from a source whose freshness the identity ADR
  of BP-002 decides (§9). Whether a level lost while a request waited refuses it (BP001-AC-10)
  depends on that freshness.

## 5. Security guarantees

- The subject, its transaction scope and its trust boundary: ADR-ARCH-032 §3, ADR-ARCH-033 §4.
  Insert order, the paired workspace visibility and `access.may_act_in`: ADR-ARCH-033 §5. Exactly
  one current owner: ADR-ARCH-033 §6.
- Policies for `saasbtp_api` on the Access tables (`sql.md` RLS); every command not listed has no
  policy, and is therefore refused:

  | Table | Insert admits | Select admits |
  |---|---|---|
  | profiles | the subject's own profile | the subject's own profile |
  | ownerships | an ownership naming the subject's profile | the subject's own ownerships |
  | organizations | any row (ADR-ARCH-033 §5) | organizations whose current owner is the subject (§3) |
  | memberships | a row naming the subject's profile, under an organization the subject currently owns (ADR-ARCH-032 §4, ADR-ARCH-033 §5) | the subject's own memberships |
  | workspace_accesses | a row naming the subject's profile, under an organization the subject currently owns (ADR-ARCH-032 §4, ADR-ARCH-033 §5) | the subject's own accesses |
  | workspaces | as ADR-ARCH-033 §5 | as ADR-ARCH-033 §5 |

  The select policy of ownerships reads no other table, so that the organization's select
  policy can read it without recursion.

  BP-001 creates no `UPDATE` or `DELETE` policy on any Access table: no founded record can be
  changed or removed through the API until a process adds one.
- Rules the policies do not hold, enforced by the domain and proven by its tests (ADR-ARCH-032 §4):
  the founder's access covers the first workspace only (BP001-R4); ownership and membership grant
  no access (INV-ACCESS-05).
- A relation is current until its end is recorded. Memberships and workspace accesses carry,
  from BP-001, a nullable end, and their unique keys are restricted to rows without one; no
  process of BP-001 sets it.
- Refusals reveal nothing beyond "in use" or "not found" (ADR-ARCH-032 §5, INV-ACCESS-09).

## 6. The client's founding-request store

What TSK-1, TSK-2, BP001-R6 and BP001-D2 require of the client application, without naming a
technology:

- A request is keyed by its reference, assigned when the description starts, and kept until it is
  answered 201 or 200, or abandoned; it survives closing the application and the loss of the
  connection.
- It belongs to the identity provider's user who described it. It is shown and submitted only
  while that user is signed in.
- After its first submission its names cannot change, except after a 422.
- 403, 401, 500 and the absence of an answer keep it unchanged and resubmit the same request once
  possible; after repeated failures the founder is told and may abandon. 409 gives it a new
  reference and keeps its names. 400 is a defect of the client: the request is kept, not
  resubmitted, and the founder is told.
- The company name is offered as the default first workspace name.

**Not covered by the pilot #138**, which delivers the backend: BP001-AC-02, 07 (the description
kept), 12, 16, 18, 22, and the device part of BP001-AC-10. BP001-R6 is therefore not verified
until the client is built.

## 9. Open points

Cited, not decided here:

- Token validation in the API, and where the "confirmed contact" level is read and how fresh it
  is: the identity ADR of BP-002. Every proof of §7 marked "pending the identity ADR" is
  written once it exists.
- The audit columns of the Access tables other than `created_at`: #184.
- MicroKit.Result and MicroKit.Persistence declared sound before implementation (ADR-ARCH-035 §2).
- The format of the API's error bodies: no decision sets it. This contract fixes only what each
  answer reveals.
- Abuse protection, including any rate limit: open question of `process.md`; no `429` is part of
  this contract.
