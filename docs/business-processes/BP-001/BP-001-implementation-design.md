# BP-001 — Implementation Design

Status: durable design contract (software model). Pairs with `BP-001-design-package.md`.
Purpose: state the software-level decisions that constrain any faithful implementation of the BP-001
business model, while leaving any developer or AI free to derive their own Implementation Plan. This
document answers "how must software carry the model", not "in what order will it be built".

Scope. Contains only decisions that constrain a faithful implementation — each derived from the
Design Package or already fixed by an ADR. It contains NO execution plan, no task breakdown, no
file-creation order, no tool-specific prompt. Anything resembling an execution step belongs to the
(non-consigned) Implementation Plan derived from this contract. The Implementation Design must permit
several valid implementations while preventing interpretations that violate the business model.

Inputs (upstream, closed): `BP-001-specification.md`, `BP-001-design-package.md`.
Cross-cutting decisions referenced: ADR-ARCH-001 (OpenAPI contract), ADR-ARCH-005 (write path +
identity-provisioning exception), ADR-ARCH-006 (DbUp owns DDL), ADR-ARCH-011 (createUser Admin API
onboarding), ADR-ARCH-013 (authorization scope levels; BP-001 consumes only the Workspace grain).

---

## §1 Software Architecture Model

The participants of BP-001, by role (not by concrete form). A faithful implementation must place
these responsibilities somewhere; the naming here is by responsibility, not by class or framework.

| Role | Responsibility | Boundary |
|---|---|---|
| **Trigger actor** | Carries the founding intent (identity to establish + organization context). Executes no internal operation. | Outside the system (the founder). |
| **Founding application service / handler** | Orchestrates the full sequence; decides the order; owns the business transaction; guarantees all-or-nothing. The only participant that sees the whole process. | Application layer. |
| **Identity boundary** | Establishes the auth identity (`createUser`) BEFORE and OUTSIDE the business transaction. Returns a recognized identity. | Port to GoTrue (Admin API). |
| **Transaction owner** | Opens / commits / rolls back the atomic unit. The switch point is the commit. | Owned by the handler (unit of consistency). |
| **Writers** (one per element: identity projection, organization, workspace, ownership, membership, workspace access) | Each writes its element with values ALREADY present (ids/timestamps not generated by the database). Do not generate, do not orchestrate. | Persistence layer. Concrete strategy constrained by ADRs (see §6). |
| **Rollback boundary** | On any failure INSIDE the transaction, no business fact persists. The auth identity may remain orphaned (accepted). | The transaction itself; triggered by the handler. |

Interaction sequence:

```mermaid
sequenceDiagram
    participant F as Founder
    participant H as Founding handler
    participant ID as Identity boundary (GoTrue)
    participant TX as Transaction owner
    participant W as Writers (projection + five facts)

    F->>H: founding intent (identity + organization context)
    H->>ID: createUser (OUTSIDE the business transaction)
    alt identity cannot be established
        ID-->>H: failure
        H-->>F: failure — no business data
    else identity established
        ID-->>H: auth identity
        H->>TX: BEGIN
        H->>W: write identity projection
        H->>W: write organization (Declared)
        H->>W: write workspace (first)
        H->>W: write ownership
        H->>W: write organization membership
        H->>W: write workspace access
        alt a write fails
            H->>TX: ROLLBACK
            Note over TX,W: no business fact persists; auth identity may remain orphaned (accepted)
            H-->>F: failure
        else all succeed
            H->>TX: COMMIT
            H-->>F: organization usable by its founder
        end
    end
```

## §2 Domain → Software Mapping

Each business element of the Design Package mapped to a software responsibility, and — separately —
each invariant mapped to the single component that guarantees it (no invariant guarded redundantly in
two places).

| Business element | Software responsibility |
|---|---|
| Founding trigger + orchestration | Founding handler (application layer) |
| `createUser` (out of tx) | Identity boundary, called before BEGIN |
| Transaction boundary / commit switch | Transaction owner (unit of consistency), held by the handler |
| Identity projection (`profiles`) | Persistence write (projection, not a business fact) |
| Organization (Declared) | Persistence write (autonomous unit) |
| Workspace (first) | Persistence write (autonomous unit, bound to organization) |
| Ownership / Membership / Workspace Access | Persistence writes (autonomous persisted relations) |
| Id / timestamp values | Present before the write (see §3.5); the database does not produce them |

Invariant → guarantor:

- **Persistence (structural constraints):** valid references (a relation points to an existing
  projection/unit); uniqueness of a binary fact — `(profile, workspace)`, `(profile, organization)`,
  one ownership per organization.
- **Transaction boundary (atomicity):** all-or-nothing over the projection + five facts (no active
  workspace without owner; membership and access exist only within the committed whole).
- **Application/domain orchestration (process rules):** founder = requester (relations are attached
  to the identity that triggered the process); createUser out of tx then the facts within it;
  Organization Status = Declared carried at write time.

## §3 Persistence Design

A persistence contract — the persisted model and the constraints it imposes — with no DDL, no SQL
types, no migration. Each decision answers a Design Package constraint, not an implementation
preference.

### 3.1 Persistence boundaries: autonomous / relation / projection

| Persisted element | Nature | Design Package constraint imposing it |
|---|---|---|
| **Organization** | Autonomous unit | Business fact with its own identity and lifecycle (Status = Declared). |
| **Workspace** | Autonomous unit, bound to an Organization | Business fact; Organization 1:N Workspace; own identity. |
| **Ownership** | Persisted relation (Person↔Organization) | A distinct axis (property), never an attribute of Organization or Person. |
| **Organization Membership** | Persisted relation (Person↔Organization) | A distinct axis (belonging); derives from nothing. |
| **Workspace Access** | Persisted relation (Person↔Workspace) | A distinct axis (authorization), at the Workspace grain. |
| **`access.profiles`** | Identity projection | The Design Package declares it infrastructure, not a business fact; projects `auth.users`. |

Design decision (the one that makes the persistence derivable by anyone):

> The three relations (Ownership, Membership, Workspace Access) are persisted as **autonomous
> persisted relations**, NOT as internal components of Organization or Workspace.

Justified by constraint, not doctrine: the Design Package requires the three axes to be separate and
non-derived, and Workspace Access to be revocable independently — which a model embedding access as
an attribute of the Workspace could not guarantee without coupling lifecycles. An implementation that
folded Membership into Organization would violate the separation of axes. Left free: how each element
is technically mapped (class, record, tuple), and whether Organization+Workspace form a single
domain-side transactional aggregate.

### 3.2 Consistency and transaction boundaries

- A single transaction boundary spans the `profiles` projection + the five elements. The terminal
  state is valid only if all are present together; no faithful implementation may commit a subset.
- `createUser` is outside that boundary, before it. A business failure may leave an orphaned auth
  identity; never the reverse (a workspace without owner is forbidden).
- The founding flow never intentionally commits the `profiles` projection without the business facts
  — same transaction boundary.

What this constrains: any implementation must have ONE transactional unit of consistency covering the
six writes. What that unit IS technically (unit of work, explicit SQL transaction, ORM transaction)
is free, except where an ADR fixes it (§6).

### 3.3 Conceptual dependencies between persisted elements

An integrity constraint, not an execution order:

```
profiles         (identity projection; referenced by access relations)
organization     (root; referenced by workspace + ownership + membership)
workspace        (references organization; referenced by workspace access)
ownership        (references profile + organization)
membership       (references profile + organization)
workspace access (references profile + workspace)
```

A relation cannot reference an absent element. Every implementation must respect this integrity
dependency, whatever physical write order it chooses within the transaction.

### 3.4 Necessary uniqueness and reference constraints

Only those the Design Package imposes as invariants (not convenience indexes):

- Valid references: each relation references an existing projection/unit (the six links in §3.3).
- Uniqueness `(profile, workspace)` for Workspace Access: "can act here" is binary. Removal rule:
  only if a future concept qualifies the relation.
- Uniqueness `(profile, organization)` for Organization Membership: belonging is binary. Same removal
  rule.
- Uniqueness of ownership per organization: an organization has exactly one initial owner.

These are model constraints; their physical form (unique index, named constraint) is free.

### 3.5 Generation rules and persistence principles

Derived from fixed conventions:

- Ids and timestamps **exist before the write** — never `DEFAULT SQL`, never database-generated. WHO
  generates them (domain, service, factory) is free; persistence writes values already present.
- Identifiers follow the UUIDv7 convention where required by the owning bounded context.
- Timestamps are `*_utc`, domain-stamped (fixed convention).
- Projection vs relation vs unit: a projection (`profiles`) is written but is not a business fact; a
  relation is autonomous and revocable per its nature; a unit has its own lifecycle.
- Asymmetric revocability: Workspace Access MUST be revocable without destroying history; Organization
  Membership does NOT decide its revocability (no current process produces it). An implementation may
  not make Workspace Access irrevocable, nor impose a revocation form on Membership.

### 3.6 Decisions that will constrain any future implementation

- DbUp owns the DDL (ADR-ARCH-006): persistence does not create its schema at runtime; if EF appears,
  it is runtime-only, migrations disabled.
- The six writes within one transaction boundary (§3.2).
- The persistence strategy of the Access bounded context is constrained by existing/forthcoming ADRs;
  only ADRs constrain it. Any strategy discussed in working sessions is a candidate, not a decision:
  no generalization before the relevant ADR is written and accepted (see §6.2).

## §4 API / Interaction Contract

### 4.1 Exposed capability

One: **found a company space** — submit the founding intent and receive an organization usable by its
founder. Not a CRUD on Organization: a process capability (founding command) producing atomically the
projection + the five facts.

### 4.2 Boundaries crossed

| Boundary | Responsibility | Source |
|---|---|---|
| **Frontend** | Submits the intent (identity to establish + organization context). Does not orchestrate, does not know the write order. | Design Package (actor) |
| **Backend (.NET API)** | Receives the intent, OWNS the business orchestration and transaction. Sole holder of the whole process. | Design Package (handler) |
| **Auth (GoTrue, Admin API)** | Provisions the identity (`createUser`) OUTSIDE the business transaction, before it. | Design Package + ADR-ARCH-011 |

### 4.3 Call responsibilities

- BP-001 is an initial-provisioning capability that runs via a synchronous application call, because
  no synchronizable business data exists yet before the workspace is created. It therefore does not
  fall under the PowerSync→API write flow defined for existing operational data (consistent with
  ADR-ARCH-005, whose identity-provisioning exception covers this case).
- The call triggers: (1) identity provisioning at the auth boundary, then (2) the atomic business
  transaction. The client does not drive these two phases — it submits the intent; the API
  orchestrates.
- Response semantics: success → organization usable (the minimal context to continue); identity
  failure → failure with no business data; transaction failure → rollback, no business fact, orphaned
  auth identity accepted.
- Orphan adoption: if `createUser` reports "already exists" (422), resolve by exact-match Admin API
  lookup and adopt the orphan rather than double-create (ADR-ARCH-011).

### 4.4 Contract constraints

- OpenAPI is the contract boundary; TS clients are generated from OpenAPI, never the reverse
  (ADR-ARCH-001).
- Identity travels established by the auth boundary; the founder's identity for authorization facts
  derives from the auth context, never from the request body.

### 4.5 Left to implementation

Input/output DTO shape, endpoint name and verb, signatures, precise status codes (beyond
success/failure/orphan semantics), pagination/versioning. Named, not decided.

## §5 Security / Authorization / Sync Boundary

### 5.1 Identity / membership / access separation

Three distinct planes, never conflated in implementation.

- **Identity** — `access.profiles`, a projection of `auth.users`. "Who is this person." Neither
  belonging nor authorization.
- **Membership** — `member_of` Organization. "Is part of the collective." OUTSIDE the authorization
  path.
- **Access** — the edge at the Workspace grain. "May act in this scope." The plane used by BP-001 for
  authorization.

Constraint: no authorization decision is computed from identity or membership. `member_of → access`
and `owns → access` are forbidden (ADR-ARCH-013).

### 5.2 Grain and authorization level

BP-001 produces a single authorization relation: Workspace Access, at the Workspace grain. The
Workspace is the only authorization perimeter created by this process.

Other possible scope levels are not part of the BP-001 model. They will be introduced only by the
Business Processes that require them, and will then be modelled in their own right.

Founder Access means the person is authorized in this Workspace. It does not define a detailed set of
rights. Roles, permissions, delegations, and authorization cascades are out of BP-001 scope.

### 5.3 RLS responsibility

- The access relation governs reads; ALL consumers (.NET API, PowerSync, application) respect the
  SAME authorization expression (ADR-ARCH-013).
- Fixed constraint: RLS enabled with no policy returns zero rows SILENTLY to a non-privileged
  consumer. Any access table read by a non-privileged consumer therefore requires an explicit policy
  before that read path is considered valid.
- Policy content is implementation; the obligation is a constraint.

### 5.4 Provider responsibility

- A Workspace-grain scope port expresses, in C#, "may this person act in this workspace"
  (ADR-ARCH-013).
- Constraint: the C# expression and the SQL/RLS/sync expression must be the SAME rule — otherwise a
  silent divergence (server authorizes, device does not, or the reverse).

### 5.5 PowerSync boundary

- BP-001 itself is outside the PowerSync flow (§4.3: synchronous initial provisioning).
- But the Workspace Access relation it produces BECOMES a sync authorization source: what a device may
  synchronize will derive from a parameter query over this relation. Constraint: the Workspace Access
  relation must be publishable and readable by PowerSync under RLS (ADR-ARCH-013).
- Publication mechanics and parameter-query shape: implementation.

### 5.6 Agreement test (binding obligation)

The rule "may act in this workspace" is expressed in C# (provider) and in SQL (RLS + sync). Any
faithful implementation MUST prove their equivalence on the same dataset (Testcontainers), or a
silent divergence occurs (ADR-ARCH-013). The test itself is an implementation artifact; its EXISTENCE
is a constraint.

### 5.7 Auth boundary

Identity provisioned outside the transaction (GoTrue Admin API, ADR-ARCH-011); the founder's identity
for authorization facts derives from the auth context, never from the body.

### 5.8 Left to implementation

RLS policy content, PowerSync parameter-query shape, provider code, agreement-test form, publication
mechanics. Named, not decided.

## §6 Technical Constraints & ADR candidates

### 6.1 Constraints that limit any faithful implementation

Consolidation — each line is already derived from the Design Package or fixed by an ADR elsewhere in
this document.

- DDL outside runtime: persistence writes into an existing schema, does not create it (ADR-ARCH-006).
- Ids/timestamps exist before the write: never `DEFAULT SQL`; UUIDv7; `*_utc` domain-stamped.
- One transaction boundary: `profiles` projection + five facts, atomic; `createUser` outside it.
- Three autonomous persisted relations, not embedded in Organization/Workspace; axes separate,
  non-derived.
- Integrity constraints: valid references (six links); uniqueness `(profile, workspace)`,
  `(profile, organization)`, one ownership per organization.
- Authorization at the Workspace grain only for this process; identity/membership outside the
  authorization path.
- One authorization expression shared across C#/RLS/sync, proven equivalent (agreement test binding).
- RLS enabled ⇒ policy mandatory from the first non-privileged read (else silent zero-row).
- OpenAPI as the contract source; authorization identity from the auth context, not the body.
- Identity provisioning via GoTrue Admin API (createUser), orphan adoption on 422.

### 6.2 ADR candidates (to be written; not fixed here)

New technical decisions BP-001 will require, to be consigned as ADRs when written — named, not
decided:

1. **Persistence strategy of the Access bounded context.** To be formalized by ADR if required; only
   ADRs constrain it. No generalization before the ADR is written and accepted — any strategy raised
   in working sessions is a candidate, not a constraint.
2. **Technical realization of the founding transaction boundary.** The atomicity of the projection +
   five facts is already a business decision (Design Package); what may become an ADR is HOW that
   atomicity is achieved technically, if it is a new choice beyond ADR-ARCH-005.
3. **Fate of the legacy `access.memberships`** (migration / rename / replacement) — tied to the
   still-to-be-written amendment of ADR-ARCH-008/009. ADR-ARCH-013 records the divergence; the
   concrete patch is deferred.

None is decided here. They are named so that a deriving developer or AI knows what remains to be
formalized before or during implementation.
